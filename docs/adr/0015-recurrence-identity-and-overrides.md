# ADR-0015 — An occurrence is identified by its slot, not by its time

**Status:** accepted · 2026-08-17

## Context

Stage 6 adds recurring events. Dates already live in `qevm_occurrences`
([ADR-0003](0003-occurrence-table.md)), derived from post meta and regenerated by
`OccurrenceSync` on every save of the event.

Regeneration reconciles by start time. `OccurrenceRepository::replace_for_event()` builds
a map of existing rows keyed on `start_utc`, updates the ones the new set still contains,
and deletes the rest — with a comment saying that the start "is what identifies a date
within an event".

That is true for a one-off event, where the only way to change the date is to change the
event. It stops being true as soon as a single occurrence of a series can be moved on its
own, because moving it changes the very field being used to recognise it. A moved
occurrence looks like two facts to the reconciler: a date the event no longer has, and a
date it has newly acquired. It deletes the first and inserts the second, so the override
is destroyed and the row identity is replaced — on the next save of the event, for any
reason, including an unrelated typo fix.

Nothing has noticed because nothing yet points at an occurrence row.
`registrations.occurrence_id` and `attendees.occurrence_id` have existed since C1.5 and
C1.6 and are still written as `0` on every insert. Stage 6 is where they start carrying
real values, which means the row-identity bug and the feature that makes row identity
matter arrive in the same stage.

A second question sits behind the first. If one occurrence can differ from its series, how
much can it differ? The occurrence table holds times and a status. The title, content,
venue and capacity live on the post that every occurrence in the series shares. So a
per-occurrence *time* has somewhere to live and a per-occurrence *title* does not.

## Decision

**Occurrences generated by a rule are identified by the slot they came from, in a new
`recurrence_id` column, and reconciliation matches on it rather than on `start_utc`.**

```sql
recurrence_id datetime DEFAULT NULL
```

- Set once, when the row is generated, to the UTC start the rule produced.
- Never changed. Moving an occurrence changes `start_utc`; the slot it belongs to is
  still the same slot.
- `NULL` for a non-recurring event's single row, which keeps reconciling by start time as
  it does today.

The name is [RFC 5545's `RECURRENCE-ID`](https://datatracker.ietf.org/doc/html/rfc5545#section-3.8.4.4),
which exists for exactly this and means exactly this. Adopting the name costs nothing and
makes the iCalendar export in a later release a copy rather than a translation.

`is_exception = 1` gains a precise meaning it did not have while it was an empty column:
**the rule no longer owns this row's times or status.** Regeneration matches the row,
leaves those fields alone, and moves on.

**And: a per-occurrence edit may change when a date happens or whether it happens, and
nothing else.**

Times and status are per-occurrence. Title, content, venue, capacity and registration
settings are per-series, and editing them at "this occurrence" scope is not offered.

## Alternatives considered

**Match on start time and forbid moving an occurrence.** Keeps the current reconciler
untouched. Rejected because "move one instance" is most of what recurrence editing is for
— the meeting that clashes with a bank holiday is the reason people want the feature.

**Match on row id, held in a per-event list of exceptions in post meta.** Works, and puts
the mapping somewhere it has to be kept in step with the table by hand. A derived table
whose identity map lives in serialised meta is two sources of truth with no constraint
between them.

**Detach a modified occurrence into its own post.** The model Google Calendar presents and
the one that allows a per-instance title. Rejected for 26.0 on consequences rather than
difficulty: a detached instance silently stops receiving series edits, so "change the
venue for all of them" quietly skips the one somebody customised in March, and there is
nothing on screen to say why. Doing it properly means showing detachment in the UI,
offering re-attachment, and deciding what re-attachment does to the customisation. That is
a feature, not an implementation detail, and half of it is worse than none of it.

The cost is real and worth stating: an organiser who wants one instance titled "Christmas
special" cannot have it. They cancel that occurrence and create a separate event, which
works, takes four clicks, and is honest about what it is doing.

**Store overrides as a JSON blob on the occurrence row.** Solves per-instance titles
without a second post, and makes every renderer read two sources for every field. The
occurrence table is read by the archive, the calendar, the REST API and the structured
data, all of which currently read the post for content and the row for dates; giving the
row an optional shadow copy of the post's fields puts a fallback branch in each of them.

## Consequences

- `qevm_occurrences` gains one nullable column. Adding it in C6.2 rather than C1.2 means
  a `dbDelta` on an existing table, which is what the schema version mechanism is for —
  and which C5.1 has just demonstrated is easy to forget, so it comes with a
  `QEVM_DB_VERSION` bump in the same change.
- `replace_for_event()` gains a second matching mode. The one-off path is unchanged, so
  existing behaviour and its tests stand.
- `is_exception` becomes load-bearing rather than reserved. Any code path that writes an
  occurrence has to preserve it.
- An exception surviving an unrelated save becomes a required test. Every other recurrence
  test passes with this bug present, because they act on an occurrence and then look at it
  immediately, which is precisely the window in which the bug is invisible.
- Per-occurrence content overrides are closed off until a later release deliberately
  reopens them, by superseding this ADR rather than by adding a column.
